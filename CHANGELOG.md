# Changelog

All notable changes to GK Records are documented in this file.

## 1.07.000 (2026-11-17)

### Changed

* A table value counts an empty cell as a missing one, on the instance's row and on a person's, and keeps a text cell without the spaces around it, as a text value is kept. A save that changes nothing that holds is not saved and writes no event.
* An appearance event names a table's cells and values in the words of the page that owns them, given at the registration (`cells:`, with `blank:` for what counts as empty). An empty cell reads as the page's word for the empty choice, never "none", and an id that is gone reads as the stored value followed by "(no longer exists)". A cell the page no longer knows is said in the word of the cells beside it only when every one of them has that word and they all agree; otherwise its empty side reads "empty" and its value as stored.
* The neutral word for an empty table cell ("empty") is GK Records' own, and the page that owns the table uses it, so that Save's popover and the event log say it alike.
* The latest change shown for an appearance setting is the newest event that changed something. An older event whose rows were all empty is passed over there, and the event log still lists it as "Nothing changed". Each setting is looked back in on its own, up to 500 earlier events, so many empty events of one setting never hide another setting's change.
* An appearance event shown with nothing left to show, its rows empty on both sides, reads "Nothing changed". This holds also for a list or a text in an event written before; events already written are not rewritten.
* A list value marks what was removed with − and what was added with +, also in the CSV and the search.
* A cell the owning page no longer knows (a button or a tracker that is gone) is kept by a save that did not concern it.
* GK Signoff's listener on new events (`gk_signoff`) is reached also while GK GUI Stuff is missing, too old or not active, as the listeners of the plugins released with GK Records are. A GK Signoff that makes its sign-off requests by itself in that state therefore still makes them; a GK Signoff that listens only while GK GUI Stuff is active is not affected. GK Triggers is still passed over in that state.
* The verification places of GK Records, the issue default and the assessments, are registered also while GK GUI Stuff is missing, too old or not active. An issue's place is then locked to the review as it is otherwise: Verified can be set only through an approved review, never by hand. Nothing more is shown in that state.

## 1.06.000 (2026-11-16)

### Added

* Verification status has one ladder for every place, with fixed keys: `none`, `hypothesis`, `unverified`, `partly_verified` and `verified`, in that order (`GkRecords::Verification::LADDER`). No Status, Unverified and Verified are always on; Hypothesis and Partly verified are optional per place. No plugin and no administrator can add, remove or reorder steps; stored statuses keep their keys.
* A place is where a row stands: `issue:<tracker_id>` for an issue (each tracker, falling back to the issue default `issue`), `gk_records_assessment`, and the places other plugins register. `register_content` takes the keywords `title:`, `words:`, `optional_on:`, `review:` (`:always`, `:never` or a callable with the thing) and `manage:`, which has no effect yet because the levels are set by an administrator on the pages where the place is set up; the two-argument form works as before. Records registers `issue` and `gk_records_assessment` itself. New methods: `place(obj)`, `levels(place)`, `title(place)`, `label(step, place:)`, `pill_label(step, place:)`, `review_locked?(obj)`, `check_levels`, `apply_levels!`, `set_level!`, `with_posted_settings`, `posted_settings` and `save_words!`.
* Each place's choices are kept in the setting `verification_places` of GK Records; GK Records' settings form never writes back an old copy of them, and every change is logged in the settings' history.
* The optional levels are plain check boxes where the place is set up (the partial `gk_records/verification_levels`), saved with that page's own Save: on a tracker's page under its check box Verification status, also for a tracker not created yet (it gets its levels once it is created, and has no records), shown while that check box is ticked; in GK Records' settings for the issue default and the assessments; and on the settings pages of plugins that register places. Forced levels are shown ticked and disabled. Nothing is saved when a box is ticked. Unticking a level that has records opens a box with their number, the levels they may move to (Verified only where the place does not lock it to the review), a reason as the reason place `records.verification` asks for it, and Move and switch off when the page is saved, or Cancel, which ticks the level again. When the page is saved, every place is checked first: a level switched off with records needs a level that stays and a reason where `records.verification` requires one, judged by the settings the same page posts (a review rule that reads one of them, such as GK People's, sees the new value); when something is missing nothing is saved, and the page is drawn again with what was posted, an error that names the level and its box open again. A level unticked on the page is not offered as a target. Then the records are moved in one transaction, each with an event carrying the reason and, for issues, a history entry that sends no mail, and only then the level is switched off. Should the move fail after the page was saved, the records and the levels stay as they were and the page says so, with no server error. An optional level that is off but still has records on a place stays listed there, ticked, until they are moved, and its box also offers Keep the level, which switches it on again with the page. Only records whose thing still exists are counted and moved. A tracker that keeps the levels it follows from the issue default goes on following it.
* The words of each level and the row's name per place and language are changed under Translations in GK Fields, on the tab Verification status (GK Records), with one key per place and level (`gk_records_verification:<place>:title`, `gk_records_verification:<place>:<step>`). The words resolve without that page being on.
* An event or note can have the origin `move`.
* register_event takes rows:, a lambda that gives an event kind's changes in words; the event log, its CSV export, the search and the changes column show them. Kinds.event_rows? says whether it is available.

### Changed

* The row Verification status is a pill with a dot in the status's role (No status quiet, Hypothesis notice, Not verified warning, Partly verified info, Verified saved with a lock), with "changed <date> by <name>" in quiet text after it, never italic text, a link Change status or a list. For whoever may change the status the pill is a button with ▾ that opens a box under it with GK GUI Stuff's fly (a sheet below 899 px): the steps as pills, No status first, the current one ringed, Verified dashed with a lock and the line about the review where GK Signoff is installed, never chosen by hand, the tooltip "Back to <step>" on the steps before the current one, Save and Cancel side by side and the reason under them. Save is grey until another step is chosen and, when the reason is required, written; with reasons off a click on a step saves at once. Saving shows Saving…, Saved or Not saved with the reason in GK GUI Stuff's save stripe, and after a failure the box opens again with the step and the reason kept. The arrow keys move between the steps, Ctrl+Enter saves and Esc closes. Whoever may not change it sees the pill without ▾ and box, with a tooltip that says so.
* Review requested and Changed since the review are flags of their own after the pill ("waiting for n of m"). After a failed save the box opens again with the step marked, and it is not sent again by itself. Moving the step while a review is open asks first and then takes the request back (a reviewer gives `open:` and `withdraw:` to `register_reviewer`).
* The change in an issue's history and in Events reads "Verification status changed from <pill> to <pill>", the reason as the entry's note; the note is found by core's own id for it (`journal-<id>-notes`). The badge in lists and the assessments' compact table is the pill without ▾. The issue list's column Verification status shows the same pill; CSV and PDF exports keep the status as a word.
* The issue list's filter Verification status also offers No status as a value of its own.
* Every place shows its own levels and words: the row, the pill, the box (a level that is off is left out), the history entry (in the words of the issue's tracker now), Events, the issue list's column and filter, CSV and PDF, and the assessments' table, which now shows the column only where an assessment has the row. The column's caption and the filter's values are the issue default's when the list mixes trackers and the tracker's when the tracker filter is locked to one; the filter still asks on the keys.
* Where a place does not lock Verified to the review, whoever may change the thing sets it by hand, and the box says so; `change` refuses a level that is not on at the thing's place. `set!` accepts every step of the ladder whatever the place has on, and refuses Verified without an approved review only where the place locks it.
* The help texts in the box are built from the place's words, and so are the tooltip of Changed since the review, the pill's tooltip for whoever may not change it and the refusal where the row is not used.
* Changed since the review is shown only where the place sets Verified through the review; a thing verified by a review before its place went over to by hand shows no such flag.
* For whoever may not change the status, the pill opens the box only where the review part has something to show (the place sets Verified through the review, or a review is open).
* One thing's box offers the forced levels, the optional levels that are on, and the thing's own status when that is a level that is off; `change` refuses a level that is off on any other thing.
* Events' text column, the Events CSV and the event search name a change of the verification status in the words of its place ("Verification status: Hypothesis > Partly verified"); the API keeps the keys. The places of the issues in a list of events are found in one query.
* GK People is listed among the plugins that use verification status.
* The lists are GK GUI Stuff's table: the links of a thing, the assessments, the events, the preview of Read in documents, the readings, a reading's files and objects, the columns of the document list and the registered targets on the settings page. Text stands from the start edge and in the middle of the row, and below 899 px every row is stacked.

Each group is a row of the table with a fold button and a count that leaves out the voided links. The reason of a link made by hand is in the soft text tone, and the status column is in the soft text tone, upright. A closed status is core's closed badge, kept on one line by the table's cell.

The mode of the installation stands in a box of its own at the top of the form, with the choices Each place for itself, Off everywhere, Optional everywhere and Required everywhere, and is saved with the same Save and the same reason as the places. The table under it has only places: what holds now is a column of its own, and each place's mode is a radio button in a column per mode (By the system setting, Off, Optional and Required), with the word Default under the place's default. Below 899 px the four modes of a row stand two and two. While the installation is set to one mode everywhere, the places' radio buttons stay in their columns, switched off, and one line over the table says that the places' own choices remain but do not hold now and cannot be changed here. The places' rows open and lock with the choice in the box before anything is saved, and while one mode everywhere is chosen and not saved the line says that it will hold for every place when the form is saved. Each place for itself and changes to the places can be saved together; a save that sets one mode everywhere and also changes a place is refused, and nothing of it is saved. A group's count is its number of places. Changed rows are marked, the bar at the bottom says what has changed, and Save takes one reason for every change. While the place for the reasons' modes is Off, Save opens the box with the changes without a field for a reason, and none is kept with the events; the line at the top of the page says that Off holds everywhere, also on Appearance, Functions and this page, and that an act that always asks still asks and keeps its reason. ## 1.05.000 (2026-11-06)

### Added

* The register of appearance settings: every GK plugin declares here what it changes in how Redmine's pages look or behave, each setting with its group, its levels (Off, Optional, Forced, or only Off and Forced for a setting that applies to all or none), its values and GK's proposal. Every setting is off until an administrator sets it, and a setting nobody declared is off. Every change by an administrator is an event on the setting with its reason. A person's own choices about the optional settings, and Like Redmine for me, are kept here too, each change an event of its own kind without a reason. A new table holds the levels, the values and the persons' choices. A number value outside its minimum, maximum or step is refused. A setting Redmine has its own setting for can give it with `core_link:`, as the words of its path and the path. On a person's page a setting's segment starts with Off only where its registration asks for it (`person_off:`). A value can have a quiet help text under it (`info:`).
* The event log can be filtered by the target's id, so that the history of one thing can be listed.
* At start, a plugin whose code registers an appearance setting that its `config/registrations.yml` does not list gets a line in the log.
* A function in the register can be declared on by default (`default: true` in `GkRecords::Features.register`); it is on until an administrator switches it off, and the first switch away from the default is an event like any other. Without the keyword a function is off until it is switched on, as before.
* An installation that has data when it gets the register keeps what it had chosen: a migration moves the levels, values and persons' choices that GK GUI Stuff, GK Core Stuff, GK Tags and GK People kept in their own places before, and the three functions that became appearance settings, into the register. Each level is the one the plugins answered before, also where nothing was stored, and what always held before (the instance band, the account menu's colours, the alignment, the space before AM and PM, the note of one's own mark) is set to Forced. A number outside its new limits is brought inside them. It runs once, only while the register is empty, and only for the plugins installed; a new installation gets nothing, and the old places are left as they were. Each row it writes is an event on the setting with the reason "migration", so that the history shows where the level came from.
* An installation's start choice for its appearance (`GkRecords::AppearanceSettings.start!`, with `as_redmine` or `gk_proposal`): carried out once, before anything is set, by the same fill as the links on the appearance page. Each level it changes is an event, and the choice itself is always one event for the installation, also when no level changed; each with the reason "installation".
* Appearance settings can have a list value (one entry per line, with a maximum number of entries and a pattern each entry must match) and an action value (a button under the setting that posts to the plugin's own address, with a confirmation and the form's reason). A setting can carry a warning, and a sharper warning when one of its values holds a given entry; with `reason_when_sharp:` a save that leaves it on in that state needs a reason. An optional setting can start off for each person (`person_default: 'off'`), and a setting can have only the levels Off and Optional, for what each person chooses and nobody forces. `record_on!` writes an event on a setting's row for something done to what it keeps.
* An appearance setting and a function can say where they change something on the pages and how the change gets there: `footprint:` (`anchors:`, `elements:`, `pages:`, `adds:`, `removes:`) and `applies:` (`class`, `server`, `script`, `data`, or `none` for no visible effect) on `GkRecords::AppearanceSettings.register` and `GkRecords::Features.register`, read with `footprint(key)` and `described?(key)`. A shared value has the footprints of the settings that read it, or its own when `register_shared` is given `footprint:` and `applies:`. An anchor may only use GK's own classes, ids and data attributes, Redmine's named purposeful ones and GK Core Stuff's marks (`GkRecords::Footprint`), its parts joined only by a space; an anchor that goes by a pseudo class, a child or a sibling, a bare tag or a part of a value is left out and logged. A page type is a key such as `core.issue`, kept as text.
* The check at start also logs the settings and functions whose footprint in the code differs from the plugin's `config/registrations.yml` (`footprints:`).
* Two scenario expectations: `records_reason_mode` reads the mode of the reasons for the whole installation or a place, and `records_feature_chosen` says whether one of the functions of GK Records is chosen.
* An event in the REST API has `reason_key`, the place its reason was asked for, when it has one.
* Events can be searched by free text (the field Search in the filter row, parameter `q`), also on a project's tab, in the CSV and through the API. The search looks in what the reader is shown: the kind, the target's name, the people she may see, the changes and the reason, and never in a private field or the name of a person or thing she may not see. All words must be found. One search looks through at most 10,000 events after the other filters; the page says so when it stopped there, and the API gives `search_cut`.

### Changed

* A function can be declared with the functions it goes with and the functions it requires. Several functions switched with one reason are one transaction, and the newest switch of each function is read in one query.
* A setting or function that needs GK Readup names it as GK Readup when the plugin is not installed.
* Add link in an issue's actions menu, Import document in the Documents tab's button row and the tracker form's Verification status check box are drawn through Redmine's hooks in those places (provided by GK Core Stuff) instead of being placed by script; without those hooks the row stands under the issue's description, the link at the end of the Documents tab, and the trackers are chosen on the plugin's settings page.
* The origin line of a read-in document is drawn under its category, date and custom fields through Redmine's hook there (provided by GK Core Stuff) instead of being moved by script; without that hook it stands at the end of the document page.
* The reason field on Redmine's settings pages is drawn just after Save through Redmine's hook there, in every settings tab and on a plugin's settings page (provided by GK Core Stuff). A settings form without that hook gets no reason field, and a required reason is then not asked for when that form is saved. Whether a save needs the reason is decided from the settings view it comes from (the General tab when no tab is named); a save naming a tab no settings view is known by still needs a required reason.
* The shared reason field takes a Save button marked `data-gk-reason-save` as the one it belongs to; without a mark, Enter and the field's button height use the form's default button.
* "with manifest" beside the export links: the zip icon is drawn by Redmine's icon helper, and the CSV link is recognized by its format class where Redmine's CSV dialog is on the page.
* The events page builds its folded detail rows directly instead of rewriting their markup.
* The reason label in a verification change's history entry keeps Redmine's paragraph spacing.
* Texts say Redmine and Redmine's where they said core, core's or the Swedish word for it.
* The zip icon "with manifest" beside the export formats and the check box in Redmine's CSV dialog are now off by default, also in an installation that upgrades. To get them back, set the new row The choice with manifest at exports under Administration > Appearance (GK GUI Stuff) to Forced or Optional. The log of exports, downloads and prints is not affected, and an address with `with_manifest=1` still gives the zip.

### Fixed

* The table of places for reasons heads its first column with the plugin's name in the page's language instead of a missing translation.

A save of several functions forgets the memory after its commit.
